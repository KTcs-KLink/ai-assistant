# 맞춤 혜택 구현·실행·검증 결과

기준일: 2026-11-07 (한국 시간). 이 기록은 로컬 기능과 자동 검사 결과이며, 실제 KTcs 사규 승인이나 직원의 지급 자격 확인이 아니다.

## 바로 실행

이 PC에서는 `start_benefits.cmd` 또는 아래 명령을 사용한다.

```powershell
python scripts/launch_benefits_demo.py
```

화면: <http://127.0.0.1:8821/benefits>, API: `127.0.0.1:8820`. 실행 파일은 창을 띄우지 않는 별도 프로세스를 시작하고 화면을 브라우저에서 연다. 기존 8811/8805 실험 서버와 8000/5173 시연 서버를 변경하지 않는다. 실행 기록과 새 API의 빈 SQLite 공간은 Git에서 제외한 `.demo-logs/benefits/`에 둔다.

새 PC의 최초 설치:

```powershell
python -m venv server/.venv
server/.venv/Scripts/python.exe -m pip install -r server/requirements-dev.txt
npm ci --prefix web
python scripts/launch_benefits_demo.py --env-file C:/private/project/.env
```

이 작업에서는 기존 KTCS 루트 `.env`를 메모장에서 열었으며 키를 복사하거나 새 빈 환경파일로 교체하지 않았다. 서버만 이 파일을 읽는다. 프론트에는 키를 전달하지 않는다. 다른 PC에서 자료 경로를 지정하지 않으면 로컬 한국전력 조회는 미연결 상태를 표시한다.

화면의 GPT 결과는 **설명 초안·사람 검토 미완료**로 표시한다. 구조·인용·수치 검사는 의미 정확성과 완전성 보증이 아니다. GPT는 가상 규정 본문 하나만 받으며 직원 조건, 세션, 루트 `.env`나 로컬 실제 규정은 이 기능으로 전송하지 않는다. 재요청은 세션별 캐시로 처리한다.

브라우저에 기록된 초기 미인증 401은 세션 확인과 기존 로그인 확인 요청에서 발생했다. 이를 정상 로그인 성공이나 연결 장애로 혼동하지 않는다. 기능 검사 중 JavaScript 실행 오류는 관찰하지 않았다.

## Supabase에서 남은 연결

공개 키는 인증 서버에서 실제로 허용됐다. 초기에 REST 루트의 401을 모든 키의 오류로 해석했던 안내는 정정했다. 개인 조건 테이블의 0행 조회에서 반환된 `PGRST002`는 데이터 서비스의 스키마 캐시/DB 연결 오류이며, 정확한 원인은 프로젝트 설정·DB 로그로 확인해야 한다. [Supabase 공식 원인·복구 안내](https://supabase.com/kb/troubleshooting/postgrest-error-pgrst002-could-not-query-the-database-for-the-schema-cache-c396e9).

현재 연결 도구가 보여주는 비활성 프로젝트는 `.env`의 대상 프로젝트와 다르다. 대상 프로젝트 관리 요청은 권한 거절됐다. 관련 없는 프로젝트를 복구·수정하지 않았다. 비밀 키만 교체해 DB 오류의 복구를 보장할 수 없으며, 직원별 조회 자체는 publishable key와 직원 본인 JWT를 사용한다.

1. 대상 프로젝트 관리 권한으로 DB 상태, Data API의 Exposed schemas, 기존 테이블·보안 권고·로그를 확인한다. 확인하지 않은 스키마나 설정을 임의 변경하지 않는다.
2. `supabase/migrations/20261107005512_benefit_profiles_consent.sql`은 CLI 3.0.0으로 생성한 로컬 migration에 작성했다. **아직 어느 DB에도 적용하지 않았다.** 본인 소유 CRUD, UPDATE의 USING/WITH CHECK, 익명 사용자 제외, 미동의 조건 저장 제약을 포함한다.
3. 스키마 충돌 없이 개발 대상에 적용한 후 서로 다른 테스트 계정 2개로 본인 허용/타인 거절/소유자 변경 거절/익명 거절/삭제를 실제 DB에서 확인한다. 현재 Python 테스트의 Supabase 경계는 모의 응답 검증이며 DB RLS 실행 검증이 아니다.
4. 이 PC의 Docker 엔진은 실행 중이 아니어서 로컬 Supabase DB도 실행하지 않았다. DB 정책 실행 검증을 통과했다고 표시하지 않는다.

직원용 인증 세션은 기존 공용 시연 채팅·관리자 권한을 열어주지 않는다. 실제 SSO/직원 조직 매핑, 인가된 HR 동기화, 운영 로그인 제한·감사·보존기간은 별도 작업이다.

## 실제 회사 적용·신청의 남은 경계

- 승인된 KTcs 현행 규정과 구조화된 필수 조건·예외가 없다. 따라서 실직원 모드에서는 모든 가상 카드를 '추가 확인 필요'로 처리하며 승인·거절을 확정하지 않는다.
- 금액·한도·일수·마감은 가상 규정의 예시다. 실수령액이나 검증된 혜택 총액을 표시하지 않는다.
- 공식 회사 양식과 신청/결재 API·권한이 없어 실제 제출을 하지 않는다. 예시 준비 목록은 항상 `submitted=false`다. 사용자가 요청한 실제 외부 양식이 과거 대화에 언급됐다는 이유로 KTcs 공식 양식으로 제공하지 않는다.
- `knowledge-mcp`는 읽기만 했으며 수정하거나 새 브랜치를 만들지 않았다. 실제 MCP 검색 연결, 데이터 재배포 승인, 운영용 pgvector RAG는 미완료다.
- 기존 원문·청크·임베딩·골든셋·평가 산출물은 보존했다. 새 임베딩이나 검색 성능/답변 의미 전체 평가를 실행하지 않았다.
