# 한전 원문 전체 도메인 → 업무 분류

인사 여부만 구분하던 자료를 실제 도메인과 업무로 정리한다. 기존 원문 청크 10,205개 전체를 대상으로 하고, 검색에서 제외되었던 인사 외 자료 6,335개도 포함한다. 작업 브랜치는 `feat/domain-workflow-classification-20261109`이며 Supabase 적재와 외부 DB 쓰기는 계속 HOLD다. PR은 생성하지 않는다.

## 보존한 기준과 범위

- 한전 원문 파일 단위 203개, 원문 청크 10,205개
- 기존 선별 원문 3,870개에서 만든 검색 조각·임베딩 8,511개
- 기존 서비스 답변 근거 528개 원문·536개 검색 조각
- 사용자 기준 5개 도메인·34개 업무의 코드와 이름
- 원본·정규화 본문·이전 인사 분류·벡터·골든셋

원문 청킹이 완료되었다는 것과 모든 원문이 임베딩·답변 승인을 받았다는 것은 구분한다. 이번 작업에서 청크 경계를 다시 만들거나 새 문서 임베딩을 계산하지 않는다.

최종 집계는 대표 업무 연결 6,855개(일부 구간 보류 107개 포함), 업무 판단 보류 3,339개, 개인정보 패턴 보류 11개로 합계 10,205개다. 82개 경로 중 78개에 대표 자료가 있다. 나머지 경로에 자료를 만들어 채우지 않는다.

## 분류 체계

| 구분 | 도메인 |
|---|---|
| 기존 사용자 기준 | 01 인사/근태, 02 총무/행정, 03 재무/회계, 04 IT/보안, 05 경영기획/성과관리 |
| 원문 정리용 확장 | 06 안전/보건/환경, 07 감사/윤리/법무, 08 전력영업/공급, 09 전력설비/건설, 10 연구/기술개발 |

기존 인사 공통 업무와 확장 업무를 포함해 82개 업무 경로를 사용한다. 확장은 자동 정리를 위한 제안이며 조직의 공식 분류로 표현하지 않는다. 구매·계약은 기존 기준에 따라 `02.07`, 휴가는 `01.05`에 유지한다.

한 원문에 여러 직접 업무가 있으면 복수로 연결한다. DIRECT는 실제 처리·규정하는 업무, RELATED는 관련 업무, REFERENCE_ONLY는 단순 참조다. 관련·참조만으로 대표 업무를 정하지 않는다. 대표 폴더는 각 원문을 한 번씩 세기 위한 위치이며 복수 연결을 삭제하지 않는다.

## 처리 과정과 증거 경계

Codex/코드는 전체 파일·원문 위치·해시·분류 코드·인용·중복·누락·출력 경계를 검사한다. 기존 `.env`의 `gpt-6-luna`는 실제 본문의 도메인·업무 분류를 제안한다. 키나 직원 프로필을 모델 입력·산출물·브라우저에 넣지 않는다.

긴 원문은 기존 경계를 유지하면서 검토를 위해 연속 구간으로 나눈다. 제목·상위 문맥은 참고하되 문서 대표 분류를 모든 본문에 상속하지 않는다. 생성 모델의 실제 입력 토큰을 집계하고 한도가 넘으면 요청 묶음을 나눈다. 본문을 잘라 버리거나 조건을 생략해 요청 한도를 맞추지 않는다.

각 업무는 원문 인용과 위치를 가진다. 임직원이라는 단어만으로 입찰업체·협력회사 기술자를 내부 인사로 분류하지 않는다. 전기요금 정산을 직원 급여로, 설비 유지보수를 일반 사옥 시설관리로 바꾸지 않는다. 단순히 계획·위원회라는 말이 있다는 이유만으로 경영계획이나 인사 업무로 올리지 않는다.

짧은 구조 단편, 깨진 문맥, 반복적인 제안 검사 실패는 보류한다. 개인정보 패턴 보류 자료는 본문을 모델과 공개 분리본에 넣지 않고 ID·해시·보류 상태를 보존한다. 처리하지 못한 연결 실패를 의미 검토 완료로 바꾸지 않는다.

원문 표본 대조 후 구매·계약이 누락되거나 감리 수행과 계약문서 구성이 혼동된 두 구간을 재검토하여 보완한다. 수정 전 제안과 재검토 기록을 유지한다. 같은 모델을 이용한 재검토와 인용 일치 검사는 독립적인 사람 평가나 전체 분류 정확도 측정이 아니다.

`CLASSIFIED`는 직접 업무 1개, `MIXED`는 직접 업무 복수, `PARTIAL_REVIEW`는 확인된 업무와 보류 구간이 함께 있는 경우다. `REVIEW_REQUIRED`와 `PRIVACY_HOLD`는 별도 보류 범주다. 이 상태들은 신규 답변 사용 승인·현행성·실제 KTcs 적용과 별개다.

## 산출물과 조회

기준 경로는 저장소 상위의 `outputs/klink_domain_workflow_20261109/`다. 원문 데이터·모델 호출 기록은 로컬에 보존하고 Git에는 올리지 않는다.

- `index.html`: 도메인 → 업무 선택, 문서·조문·ID 검색, 원문 미리보기, 분류 근거와 위치
- `README.md`: 집계와 업무별 실제 데이터 링크
- `by-domain/01_인사·근태/01.05_휴가/units.jsonl` 등: 읽을 수 있는 폴더명으로 분리한 원문
- `unit-classification.jsonl`: 원문 10,205개의 대표·복수 업무와 출처
- `window-classification.jsonl`: 기존 검색 조각 8,511개와 벡터 행 번호 연결
- `workflow-memberships.jsonl`: 직접·관련·참조 관계별 복수 연결
- `source-mapping-audit.json`, `source-mapping-checks.jsonl`: 부모 범위·정규화 본문과의 대조
- `protocol.json`, `taxonomy.json`, `proposals/`, `calls/`: 대상·기준·모델 제안·인용·실패 기록
- `source-sample-audit.json`, `source-review-call.json`, `source-review-overrides.jsonl`: 표본 대조와 보완 기록
- `artifact-verification.json`, `export-verification.json`, `browser-verification.json`: 전체 실자료와 화면 검사

검토 조회는 독립된 정적 화면이다. 기존 인사 답변 API와 질문별 호출 구조를 변경하지 않는다. 기존 검색 조각에는 겹치는 원문 구간의 분류를 연결하므로, `primary_has_local_support`로 실제 인용이 그 검색 조각 안에 있는지도 구분한다.

실행 명령:

```text
python scripts/classify_domain_workflows.py prepare
python scripts/classify_domain_workflows.py run --workers 4
python scripts/classify_domain_workflows.py status
python scripts/classify_domain_workflows.py finalize
python scripts/report_domain_workflows.py
python scripts/launch_domain_workflow_view.py --port 8852 --no-open
```

완료된 버전은 덮어쓰지 않는다. `quarantine`은 실제 모델 제안이 최소 3회 보존되어도 검사에서 반복 실패한 구간만 보류하며, 미처리·접근 거절·요청 제한을 완료 처리하는 용도로 사용하지 않는다. 원문 전체의 기계적 연결 검사는 의미·예외·적용 대상의 사람 승인과 구분한다.

보존된 모델 응답은 `recover_domain_workflow_proposals.py`로 새 호출 없이 다시 검사할 수 있다. 정확히 같은 중복 연결만 제거하며 문자를 바꾸는 인용 복원은 하지 않는다. 이번에는 6개 구간을 복구했고, 제안 3회가 각각 보존돼도 검사를 통과하지 못한 148개 구간은 보류했다. Windows 파일 교체 충돌에는 로컬 쓰기만 재시도하도록 보완했다. 이는 새 모델 응답을 요구하는 재시도와 구분한다.

자동 테스트 200개가 통과했다. 실자료 10,205개의 대표 폴더가 상호 배타적이며 전체 ID를 포함하고, 기존 검색 조각 8,511개와 벡터 행 번호가 보존됨을 검사했다. 실제 브라우저에서 10개 도메인과 구매·계약 업무, 복수 연결, 개인정보 패턴 보류를 확인했다. 브라우저 스크립트 오류·외부 요청·모델 요청은 0이었으며 모바일 가로 넘침은 없었다. 변경 코드와 로컬 산출물의 실제 설정 키 문자열 일치도 0이었다.

조회 서버는 로컬에서만 열고 OpenAI·Supabase 키와 비밀 환경변수를 제거한 환경으로 실행한다. 브라우저에서 모델을 호출하지 않는다. 자동 테스트, 실제 전체 데이터의 분리 검사, 브라우저 검증 및 비밀키 문자열 검사는 각각 별도 증거로 기록한다. 검색 성능이나 최종 LLM 답변 정확도를 평가한 것으로 표현하지 않는다.
