# 로컬 한전 원문 기반 인사 챗봇 연결

기준일: 2026-11-07. UI 브랜치: `feat/uiux-hr-intents-20261107`, 시작 커밋: `c4ee97333fa74ba005fac45d9731acd5de8211d9`.

대안 포털의 AI 업무 도우미를 원래 인사 개발 채팅이 관리하는 8844 서비스에 연결했다. 질문 의미 확인 → BGE 임베딩·단어 결합 검색 → 실제 한전 조문 → 지정 모델의 답변 초안·원문 대조를 사용한다. 이해한 내용은 `질문을 이렇게 이해했어요: {interpreted_as}`로 짧게 표시한다.

| 주소 | 역할 |
| --- | --- |
| `http://127.0.0.1:8825/hr/assistant` | 연결된 AI 업무 도우미 |
| `http://127.0.0.1:8844/hr-check` | 원래 채팅이 관리하는 의미 분석 인사 API |
| `http://127.0.0.1:8841` | 서버에서만 요청하는 한전 전용 질문 인코더 |
| `http://127.0.0.1:8824/workspace` | 보존된 기존 시안 |

`start_hr_portal.cmd`는 8844의 앱 식별자·품질 버전·hybrid 검색·LLM 질문 분석 설정을 확인한 뒤 UI만 시작한다. 준비된 기존 서버를 교체하거나 다른 서비스를 종료하지 않는다. 이전 8842 비교 서비스와 8833/8832 로컬 구현도 보존했다.

## 질문과 근거의 표시

`understanding.status=ready`는 해석한 질문과 규정 답변을 표시한다. `needs_clarification`은 질문 확인 상태와 확인 질문을 한 번만 표시하며 규정 답변·출처를 만들지 않는다. 범위 밖 응답도 검토 필요 상태를 유지한다.

클라이언트는 허용된 업무 ID, 원질문 보존 표시, 원질문에 그대로 존재하는 명시 조건과 응답 방식을 확인한다. 설명 생성은 분석/초안/원문 대조 단계를 사용한다. 지급일을 원문에서 직접 추출하는 `answer_method=SOURCE_EXTRACTED_FACTS`는 지정된 추출 검사 결과와 의미 분석 1단계를 허용하고, 원문에서 직접 확인한 안내임을 표시한다. 호출 횟수를 일괄 3회로 고정하지 않는다. 확인 질문 응답에 규정 답변이 섞였거나 조건·단계가 맞지 않으면 내용을 표시하지 않는다. 이 검사는 형식·출처 경계 검사이며 질문 이해의 의미 정확성을 보증하지 않는다.

기존 회사·SHA·원문 구간 복원·문장별 인용 검사와 부분/전체 보류 처리는 유지했다. 인용문은 앱이 실제 원문 구간에서 복원한 것으로 표시한다. 검색 결과에는 서버가 반환한 실제 조문을 펼쳐 읽을 수 있다. 원래 서버 응답에 개별 벡터 창 ID·점수·질문 벡터 캐시 사용 여부가 없으므로 이를 UI에서 만들지 않았다.

질문 분석 단계 추가에 맞춰 화면 제한은 540초, 개발 프록시 제한은 570초로 조정했다. 대기 중에는 질문 이해·검색·원문 대조 중임을 안내한다. 자동 재요청은 하지 않는다.

## 실제 확인 결과

[검증 자료](hr-semantic-ui-20261107/README.md)에 결과와 화면을 보존했다.

- 실제 화면에서 두 질문을 순서대로 전송했다. 모두 HTTP 200과 인용이 있는 답변을 받았다. 각 요청에 `question_understanding → draft → source_comparison` 3단계, 총 모델 생성 6회를 확인했다.
- “통상근무자의 휴게시간을 업무 사정으로 바꿀 수 있나요?”와 “일 때문에 점심 쉬는 시간을 다른 때로 옮겨도 되나요?” 모두 `work_break`, `휴게시간 운영`으로 해석했다. 원질문의 명시 조건도 유지했다.
- 두 응답은 동일한 SHA의 취업규칙 제20조와 제21조를 인용했다. 제20조 원문과 반환 본문을 읽어, 통상근무자의 원칙적 휴게시간과 업무사정에 따른 시간 변경 가능이라는 핵심 결론이 일치함을 확인했다. 두 번째 답변은 특수근무자와 변경 주체·승인 절차 미명시도 설명했다. 문구나 설명 범위까지 동일하다는 뜻은 아니다.
- 실제 응답의 이해 표시, 인용과 원문 문자열, 조건 원문의 위치, 조회 원문 전체 표시를 확인했다. 1440/768/390/360px에서 가로 넘침과 브라우저 오류가 없었다. 질문 전송 본문은 `question` 하나였으며 브라우저 Authorization 헤더와 `/api/benefits/config` 요청도 없었다.
- 보존된 실제 응답 재생 1개, 합성 원문값 추출 방식 1개, 합성 확인 질문/범위 밖 상태 2개, 조건·원질문 보존·업무 ID·단계·확인 질문에 답변 혼입·단계 배열·추출 방식의 단계 변조 7개, 총 11개 화면 검사가 통과했다. 이 재생 검사의 새 모델 생성은 0회다. 합성 확인 질문과 원문값 추출 응답은 실제 모델의 판단 성능이나 새 추출 답변의 정확도 측정이 아니다.
- TypeScript 검사와 프론트 빌드가 통과했다. 기존 일반 UI 회귀 스크립트의 범위 밖 질문도 응답 가로채기로 바꿔 의미 분석 모델을 실수로 호출하지 않게 했다. 이번의 별도 13개/42개 전체 회귀 실행은 완료 결과가 없어 집계하지 않았다.

이는 두 질문의 연결·표시·원문 대조 확인이다. 전체 검색 성능 평가, 독립 정답 평가 또는 전체 질문의 정확도 보증으로 확대하지 않는다. 원래 채팅의 별도 의도/답변 평가 수치를 이 작업에서 다시 실행한 것으로 합산하지 않았다.

## 자료와 남은 연결

실제 응답 기준으로 한전 참고자료 10문서·449개 조문이며 사람 승인 0개다. 로컬 질문 인코더의 모델은 `BAAI/bge-m3`, 차원은 1024다. 인코더 식별·고정 가중치·수치 대조 상태도 확인했다. 백엔드 소스에는 원질문 및 코드가 제한한 의미 검색어를 같은 원문 허용 목록의 벡터/단어 검색에 결합하는 경로와 벡터 오류 시 보류 처리가 있다. 질문 벡터는 메모리 캐시에서 재사용될 수 있다.

실제 두 질문을 확인할 당시 API의 기능 변경은 원래 체크아웃 `feat/hr-semantic-intents-20261107`의 로컬 미커밋 상태였다. 당시 HEAD `558b600`만으로 새 의미 분석 코드가 고정되었다고 표현하지 않았다. 원래 채팅은 이후 같은 8844에 원문값 추출·메모리 제한 변경을 적용해 재시작했다. 최종 기능 설정과 파일 지문은 별도 시각의 [서비스 기록](hr-semantic-ui-20261107/upstream-service.json)에 남겼다. 원래 백엔드 변경을 이 clone에 복사하거나 병합하지 않았다.

KTcs 규정 적용·현행성·실직원 자격·사람의 최종 승인은 확인 전이다. 직원 접속과 혜택 카탈로그는 여전히 예시이며, 공식 양식·SSO·실제 신청/결재는 미연결이다. Supabase 연결 재검증·적재·SQL 적용은 HOLD로 유지했다. 기존 시안·원문·색인·기준 평가 산출물은 수정하지 않았다.

Codex는 UI·전송 제한·응답 검사·브라우저 확인을 담당했다. 기존 앱 코드는 허용 출처 검색·원문 복원·토큰/인용 검사를 수행했다. 서버에 설정된 GPT는 질문 이해, 답변 초안과 같은 모델의 원문 대조를 수행했다. 같은 모델의 대조는 독립된 사람 승인이 아니다.

## 재현

```powershell
python -B -X utf8 scripts/check_hr_closeout_service.py
npm.cmd run dev:hr --prefix web
```

`scripts/verify_hr_intent_portal.js`는 실제 질문 두 건을 전송하므로 모델 생성이 발생한다. 보존된 실제 결과가 있는 환경에서는 아래 재생만 실행할 수 있다.

```powershell
python -B -X utf8 scripts/prepare_hr_intent_ui_replay.py
npx.cmd --yes --package @playwright/cli playwright-cli --session klink-hr-intents-replay run-code --filename=output/playwright/verify_hr_intent_ui_replay.generated.js
```

재생용 원본 응답과 생성 파일은 무시되는 `output/playwright`에 보존한다. 키·직원 쿠키 값·회사 원문 복사본을 검증 자료에 저장하지 않는다.
